# Where omp and pi load or launch code in a later session

Read date: 2026-10-24. Read-only research that set the scope of the code-loading ask; the decision and the chosen set are in [ADR-0011](../docs/adr/0011-code-loading-ask.md). This is a dated record of omp 18.12.6 and pi 0.84.3.

## Findings that change the design

1. omp has no project trust. `isProjectTrusted: () => true` (`CA/extensibility/extensions/runner.ts:1490`, `CA/session/agent-session.ts:8680`), and the type doc says "OMP performs no project-trust gating — project-level settings and extensions load unconditionally" (`CA/extensibility/extensions/types.ts:733-740`). Every project-level path below loads in the next session in that directory with no prompt.
2. pi gates project resources behind a trust store. A saved decision on the directory or any parent wins over the default, so in an already-trusted project (or under a trusted parent) a newly written `.pi/extensions/x.ts` loads silently. `<agentDir>/trust.json` itself is therefore a code-loading control: writing `true` for a path trusts it.
3. Several launch points are configuration that names a command or a file elsewhere (settings `extensions`, `shellPath`, `mcp.json` `command`, `models.yml` `!cmd`, plugin registries with `installPath`, `lsp.json` `command`). Gating the config file write is the only tractable control; the referenced executable can live anywhere.
4. Two launch points sit outside the host config trees: dotenv files that redirect the agent directory and shell options (omp), and `<agentDir>/bin/` prepended to PATH (pi).
5. Project-level roots differ in how far up they search. Native `.omp` extension, hook, tool, command, MCP and settings discovery is `<cwd>/.omp` only. Plugin roots and the project plugin registry use the nearest ancestor that holds `.omp/` or `.git/`.

## Path model

omp (`U/dirs.ts`):

- `agentDir` = `~/.omp/agent` by default (`U/dirs.ts:641`). `PI_CODING_AGENT_DIR` overrides it in the default profile only (`U/dirs.ts:496-505`); a named profile (`--profile`, `OMP_PROFILE`, `PI_PROFILE`) derives `~/.omp/profiles/<name>/agent` and ignores the override. `PI_CONFIG_DIR` renames the config root (`U/dirs.ts:329-337`).
- `pluginsDir` = `<configRoot>/plugins` = `~/.omp/plugins` (`U/dirs.ts:700-705`). It does not follow `PI_CODING_AGENT_DIR`. On Linux it moves to `$XDG_DATA_HOME/omp/plugins` only when `$XDG_DATA_HOME/omp` already exists and no agent-dir override is set (`U/dirs.ts:404-412`, `:437`). On this machine `XDG_DATA_HOME` is set but `~/.local/share/omp` does not exist, so the plugin dir is `~/.omp/plugins`.
- The generic helpers `getConfigDirs`/`configFileSources` build user bases from `os.homedir()` + `.omp/agent`, not from `PI_CODING_AGENT_DIR` (`CA/config.ts:84-88`). Custom commands, LSP and DAP config therefore read `~/.omp/agent` even when the override is set (custom commands also add `<agentDir>/commands`, `CA/extensibility/custom-commands/loader.ts:103-107`).
- Foreign user trees (`~/.claude`, `~/.codex`, `~/.gemini`, `~/.cursor`, `~/.config/opencode`, `~/.codeium/windsurf`, `~/.copilot`) are opt-in (`CA/capability/index.ts:51-60`, `:363-373`); `~/.claude` is switched on automatically when `CLAUDE_CONFIG_DIR` is set (`:371`). Project-level foreign trees (`<cwd>/.claude`, `.codex`, `.gemini`, `.cursor`, `.vscode`, `.windsurf`, `.opencode`) are not behind that gate. A provider listed in `disabledProviders` is removed entirely (`CA/capability/index.ts:303-306`).
- Machine facts (non-secret): `CLAUDE_CONFIG_DIR=/home/jonatsu/.config/claude`; user `config.yml` has `disabledProviders: [claude, ollama, llama.cpp, lm-studio]`, so `claude` sources are inert here, but `codex`, `gemini`, `cursor`, `opencode`, `windsurf`, `vscode`, `mcp-json`, `claude-plugins`/`agent-plugins` are not disabled. `~/.omp/agent` holds `AGENTS.md agents/ cache/ config/ config.yml lsp.json mcp.json models.yml rules/ skills/ ...` and no `extensions/ hooks/ tools/ commands/`. `~/.omp/plugins` holds one plugin, `@jonatsu/pi-verdict` (git-spec dependency).

pi (`PI/config.js`):

- `agentDir` = `$PI_CODING_AGENT_DIR` (tilde-expanded) or `~/.pi/agent` (`PI/config.js:405`, `:420-426`). The project dir is `<cwd>/.pi` (cwd only, no ancestor walk for `.pi`; `PI/core/trust-manager.js:154`).
- `~/.pi/agent` on this machine holds only `config/pi-verdict.json`.

## Coverage of the gate's current notions (for the next step)

- `<agentDir>/extensions/`, `plugins/` and agent-config files already reach the classifier as gray; this inventory lists what a deterministic ask would need to match beyond them.
- A single path set per host is not enough. Rows O2, O10, O11, P3 and P4 are keys inside broader files (`config.yml`, `settings.json`, `.env`), so a path-only ask for those files asks on every settings edit. Rows O8, O9 and P7 name a file whose whole purpose is launching processes or commands.
- Project rows depend on the session cwd. A subagent or worktree session has a different cwd, so the project-level patterns must be relative to any project root, not only the root the gate was started in.

## Near-misses checked that do NOT load code

- omp reads no `.pi` tree at all: `<cwd>/.pi/` and `~/.pi/agent/` are not scanned by any omp discovery provider (no `.pi` literals in `CA/discovery`, `CA/config.ts`, plugin loader). The `pi` key is only a manifest alias inside `package.json`. Doc comments mentioning `.pi/lsp.*` are stale; code uses the `.omp .claude .codex .gemini` list (`CA/config.ts:11-16`).
- omp markdown inputs: slash commands (`commands/*.md`), prompts, rules, instructions, `SYSTEM.md`, `AGENTS.md` (and `@` imports), agent definitions (`agents/*.md`, frontmatter carries `tools` only), skills (`SKILL.md`, only `allowed-tools` style metadata). No shell interpolation was found in the slash-command, rule or skill loaders. Inferred for prompt templates: not read in full.
- omp `getAgentModulesDir`/`getProjectModulesDir` (`U/dirs.ts:1028`, `:1171`) have no callers; `<agentDir>/modules` and `.omp/modules` load nothing.
- omp Claude-style `hooks` in `.claude/settings.json` (`PreToolUse` etc.) are not executed: those event names appear only in the extension and hook type files.
- omp `.sh`/`.py` custom tool files and `.json`/`.md` tool metadata are discovered but dropped by the loader filter (`CA/extensibility/custom-tools/loader.ts:281-285`).
- omp `ssh.json` (`<agentDir>`, `.omp`, cwd variants) defines hosts (address, user, port, key path), which `ssh` then connects to; it names no local command (`CA/capability/ssh.ts:12-28`, `CA/ssh/connection-manager.ts:197-208`). Remote reach, not host code load. `~/.ssh/config` (`ProxyCommand`, `LocalCommand`) is outside the host.
- omp `.envrc`: `direnv export` runs only for an `.envrc` the user has `direnv allow`ed; a rewritten file changes its hash, so a planted edit does not run (`CA/exec/direnv.ts:290-312`, per its own doc comment; inferred from direnv semantics). `~/.config/direnv/direnvrc` runs whenever an allowed `.envrc` loads and is outside the host.
- omp `agent.db`, `models.db`, `history.db`: SQLite state, not code. Inferred: credential rows may hold `!cmd` values, resolved by O9's resolver (`CA/session/auth-broker-config.ts:114`); the gate already treats `agent.db` as S0.
- omp `<agentDir>/config/` is pi-verdict's own config directory, not a host input.
- omp themes, keybindings: JSON. Not read in detail.
- pi has no MCP loader, no hooks directory, no custom-tools directory (`getToolsDir` has no callers, `PI/config.js:444-446`), and no project `models.json`. Pi `skills/`, `prompts/`, `themes/`, `SYSTEM.md`, `APPEND_SYSTEM.md`, `AGENTS.md`/`CLAUDE.md` are text or JSON. `~/.agents/skills` is a user resource, always trusted, and not code.
- pi's bash tool runs `bash -c` without a login shell (`PI/utils/shell.js:12-14`), so shell rc files are not read (inferred from bash semantics, no `BASH_ENV` handling found).
- Project-tooling indirection that is not a host loader: `.git/hooks/*`, `.git/config` (`core.fsmonitor`, `core.hooksPath`), `package.json` scripts, Cargo `build.rs` and `.cargo/config.toml`, `tsconfig`/build tooling run by workspace diagnostics or cleanse checkers (`CA/lsp/workspace-diagnostics.ts:198`, `CA/cleanse/checkers.ts:1244`). They run when the agent or a host feature runs those tools, not from a host config path.
